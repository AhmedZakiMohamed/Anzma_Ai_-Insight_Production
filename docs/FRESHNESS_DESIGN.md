### Existing contract rules (not redefined here)

The Core computes freshness; connectors do not send `freshness` or `communication_status` ([INGESTION_CONTRACT.md §9](INGESTION_CONTRACT.md#L567)). It uses `last_observed_at` for data age and `last_received_at` for source liveness (§9). For expectation interval `E`, the contract defines `FRESH` at age `≤2E`, `STALE` at `2E < age ≤5E`, and `MISSING` above `5E`; `UNKNOWN` means no observation has ever been received (§9). Its proposed defaults are 900 seconds for telemetry, 3600 seconds for heartbeat, and source keepalive 300 seconds; source liveness becomes `STALE` after 2× and `LOST` after 5× (§9). Backfilled old observations do not make an asset fresh (§9). The contract also states in §1 and §5 that silence is not evidence of `OFFLINE` or `UNAVAILABLE` ([§1](INGESTION_CONTRACT.md#L14), [§5](INGESTION_CONTRACT.md#L484)).

## 2. Proposed model and additive migration

**Expectations.** Add `reporting_expectations` as an override table, with explicit scope (`GLOBAL`, `SOURCE`, `ASSET`, `ASSET_METRIC`, or `ASSET_TYPE_METRIC`) and nullable scope keys guarded by a check constraint. Include `record_kind` and metric/event type keys so heartbeat expectations can be represented. Proposed fields: `expected_interval_seconds`, `stale_multiplier`, `missing_multiplier`, `active_window` (`ALWAYS` or `BUILDING_WORK_HOURS`), optional local start/end and weekdays for a series-specific window, `priority`, `valid_from`, `valid_to`, and audit timestamps. Contract §9 orders asset+metric → asset-type+metric → source → global. Adding a generic per-asset override is a requested extension; proposal order is asset+metric → asset-type+metric → asset → source → global, and it needs an explicit contract amendment before implementation. Use explicit priority within a scope and reject ambiguous equal-priority matches rather than silently choosing one.

**Defaults proposed:** telemetry `E=900s`, heartbeat `E=3600s`, stale multiplier `2`, missing multiplier `5`, source keepalive `300s`, all derived from contract §9. A source or connector may override these only through an administratively supplied expectation. An unconfigured telemetry/heartbeat series uses the relevant global interval. Event-only assets without an expected heartbeat are `NOT_APPLICABLE`, consistent with §9. Expectations default to `active_window=ALWAYS`. A configured work window gates whether a series is currently expected; outside it, expose `expectation_active=false` and do not open/advance a gap. Keep the §9 age formula in wall-clock UTC and reevaluate it when the window opens; a series may immediately be `STALE` or `MISSING` then. This preserves the contract's thresholds and avoids inventing a new freshness enum. Source-level liveness remains based on source keepalive and is not suspended by an individual asset schedule. Whether a different active-time age formula is desired would require an explicit contract decision.

**Gaps.** A `data_gaps` row represents a missing expected interval for an identified source/asset/metric (or heartbeat series), with `gap_start`, nullable `gap_end`, `cause`, `opened_at`, `last_evaluated_at`, and `closed_by`/closure time. A stable key over series + gap start makes opening idempotent. A later in-order observation that fills the interval closes it; a late/backfilled observation triggers reevaluation of the affected interval and closes or splits the gap only if the configured cadence is satisfied. Keep closed rows for audit. A rejected record is not an observation and cannot close a gap. A series with no prior observation remains `UNKNOWN` per contract §9; it is not silently relabeled `MISSING`.

**Current freshness.** Proposal: persist one `series_freshness_current` row per resolved expectation series, updated idempotently by the evaluator, containing `freshness`, `last_observed_at`, `last_received_at`, `age_seconds`, `expected_interval_seconds`, `evaluated_at`, and the expectation version used. At 1M+ facts, a precomputed current row avoids rescanning history for every dashboard read. Keep this distinct from `asset_state_current`/availability and from raw connector `equipment_state_records`; integration into Core-derived equipment state belongs to item 1.4.

**Building schedule.** Add an IANA `buildings.timezone`, local work start/end, and non-working weekdays/dates (with an explicit policy for holidays). Proposal for demo parity on existing buildings: `Etc/GMT-2`, 08:00–18:00, and no non-working days. `Etc/GMT-2` represents fixed UTC+02 and preserves the current constant-offset behavior; it is a compatibility default, not a claim about the real site. The actual customer timezone, weekend, and holiday calendar are open questions. New buildings should require an administrator-supplied timezone and schedule once the human chooses policy.

**Migration plan (proposal).** Put schema changes in a new additive migration after 008; do not edit 006–008, rewrite historical facts, drop objects, or fabricate ledger entries. Migration 006 creates `schema_migrations`; the runner takes an advisory lock, considers migrations numbered 006+, and skips ledgered versions ([apply_migrations.py, lines 24–57](../scripts/apply_migrations.py#L24)). With no ledger, its legacy branch applies additive 006 to create one, so an existing volume must first have its actual schema/ledger state checked and rehearsed before a later migration is run. The headers for 006–008 describe additive changes and no historical-fact rewrites. For existing buildings, nullable timezone/schedule columns could be added first, then backfilled to the parity defaults and made required only after an operator review; expectations and current-state tables start empty and are populated by the job. Admin-supplied values should enter via an explicit provisioning CLI or a future authenticated admin route, with validation and an audit trail; the delivery mechanism is a decision. Item 1.6's `building_code NOT NULL` is a separate identity change and is explicitly out of this proposal.

## 3. Freshness evaluation job

**Inputs.** Evaluate accepted `telemetry_records` by `observed_at` for point freshness; use `event_records` only for explicitly configured heartbeat/event expectations; read `equipment_state_records` as explicit reported evidence without letting it overwrite derived health. Use `data_sources.last_received_at` for source liveness, `last_success_at`/error fields as diagnostics, and `ingestion_batches.delivery_mode` plus `connector_status` as connector context. Do not treat a `BACKFILL` batch's receipt time as a fresh observation. Rejections are audit evidence, not operational measurements.

**Schedule and rules.** Proposal: one idempotent pass every 60 seconds, using current UTC wall time (not the latest stored fact time used by the existing pipeline), with a persisted evaluation watermark and per-source work queue. For each due series, select its latest accepted observation and apply the exact §9 thresholds. `UNKNOWN` remains distinct from `MISSING`. If `active_window=BUILDING_WORK_HOURS`, mark it not currently expected outside its local window and on non-working days; do not open/advance a gap while closed. On the next opening, apply the wall-clock §9 age formula, so a sufficiently old observation can become stale immediately. `ALWAYS` expectations continue through nights and weekends. A heartbeat expectation is evaluated as a reporting series. Source liveness uses `last_received_at` against the keepalive threshold independently of point freshness.

On each pass, upsert the current series row and open/close gaps using a deterministic series/start identity. Reprocessing the same watermark and current observations must produce no duplicate rows or alerts. A late record causes reevaluation of only its series and affected interval. The job does not synthesize `OFFLINE`, `UNAVAILABLE`, or an equipment fault from silence. It reports a source `STALE`/`LOST` liveness condition separately. Those values must not be mapped to asset availability; Core-derived equipment health/state changes are item 1.4.

**Cost and failure behavior.** Process changed sources/series incrementally rather than scanning all history each minute; process records in bounded pages (including 5,000-record batches) and persist a cursor only after the page's writes commit. Existing candidate indexes include `telemetry_records(ts)`, `event_records(asset_id, ts)`, and migration-006 `(source_id, received_at)` indexes; use `EXPLAIN (ANALYZE, BUFFERS)` on representative disposable data before proposing any index. At ≥1M rows, the 1.5 performance check must measure lag, rows/pages read, lock time, and query plans; this note makes no runtime-cost claim. If a page fails, roll it back, retain the last committed cursor, log a bounded error, and retry with backoff. If the job is delayed or stopped, freshness is marked with its actual `evaluated_at`; do not advance source timestamps or pretend evaluation succeeded.

To avoid misleading restart/outage alarms, do not reset observation timestamps on Core startup and do not open a second gap for an already-open interval. Group simultaneous stale series by source before reporting. A connector outage can legitimately make source liveness stale; once a keepalive or live batch is received, source liveness recovers while old backfill remains stale by `observed_at`. A configured startup grace for notifications (not for calculations) is a human decision; no such grace exists today.

## 4. Source-level liveness and grouped reporting

Follow the contract's proposed source thresholds: `STALE` after 2× keepalive and `LOST` after 5× (§9); with 300-second keepalive this is 600 and 1,500 seconds. Proposal for correlated impact: classify a source incident when at least 3 expected series and at least 60% of that source's active series become stale in one evaluation window. These are candidate thresholds requiring approval and calibration. Report the source code, last received time, age, affected/expected series counts, and observed connector diagnostics; restrict the detail to authorized operators.

For a correlated source issue, suppress duplicate *freshness-only* per-asset notifications and show one source-level condition plus affected assets. Do not suppress explicit fault/offline events, bad measurements, or an isolated asset whose peers on the same source remain healthy. This grouping is diagnostic only: silence never creates `OFFLINE`/`UNAVAILABLE`, and this item does not change Core-derived health/state (item 1.4).

## 5. UTC, local time, DST, and parity

Store timestamps as UTC `TIMESTAMPTZ`; ingestion already normalizes timestamps to UTC ([ingestion.py, lines 80–97](../app/services/ingestion.py#L80)). Convert to building-local time only when evaluating a configured local schedule or formatting a building-local display, using the building's IANA zone. Keep API timestamps in UTC and, if needed, add a clearly named local timestamp/zone field. Do not apply a fixed `+2` to stored instants.

The seed has no timezone values and the customer's likely zone is unknown, so a customer-specific DST example cannot be verified from this repository. Under the compatibility proposal `Etc/GMT-2`, there is no DST transition. For a future DST-observing IANA zone, test both sides of a spring-forward transition (the local clock skips a wall time) and both UTC instants mapping to the repeated wall time at fall-back; all comparisons remain on UTC instants and local schedules are interpreted through the zone database. Choose the actual zone before writing zone-specific expected timestamps.

For zero behavior change in the current demo, compare old alert output against the new schedule with `Etc/GMT-2`, 08:00–18:00, all seven days, and compare the golden alert IDs, `after_hours` facts, regime labels, and evidence for the same UTC records. Include the seed's stored `details.after_hours` behavior for CCTV motion. Require zero differences for this parity configuration; separately test a selected DST zone to prove intended local-time differences. Do not alter KPI `no_data` or hourly heartbeat-compliance calculations as part of this work.

## 6. API, dashboard, and AI exposure (design only)

Proposal: add authenticated operator read endpoint `GET /api/v1/freshness` with optional `building_code`, `source_code`, `asset_code`, `metric_code`, and `state` filters. Return `{evaluated_at, timezone, source_liveness, items:[{asset_code, metric_code, freshness, last_observed_at, last_received_at, age_seconds, expected_interval_seconds, active_window, open_gap}]}`. Add `GET /api/v1/data-gaps` for paginated open/recent gaps and their closure evidence. Use the existing operator API authentication dependency (`require_api_auth` in [`security.py`](../app/security.py#L89)); do not accept ingestion source keys for these endpoints.

Keep existing dashboard/KPI/alert response fields and meanings unchanged. A later UI may consume these new endpoints or add optional `freshness` fields to equipment-health responses; deploy additively and retain the old `no_data` semantics until separately approved. AI/chat should use freshness only as a cited, timestamped Core fact from the new read model; it must not infer faults or replace stored alert evidence. Local time display must state its IANA zone while UTC remains the stored/API canonical value. These shapes and consumer choices remain proposals.

## 7. Test and performance plan

- Unit tests: injected clock for `UNKNOWN/FRESH/STALE/MISSING`; threshold boundaries at 2E/5E; backfill does not refresh point age; source 2×/5× liveness; inactive-window gating and reopen evaluation; holidays/weekdays; idempotent gap open/close; late-data repair; DST transition instants for the human-selected zone; explicit fault remains visible under source suppression.
- Integration: run the evaluator against a disposable PostgreSQL database with representative source, telemetry, heartbeat, event, state, rejection, and batch rows; restart/replay the job and prove unchanged gap/current rows. No shared/live DB.
- Time parity: run the legacy and new alert calculations over the same demo fixture with fixed UTC+02 and 08–18/all-days; compare golden outputs and require zero mismatches before replacing the constants.
- 1.5 performance outline: synthetic ≥1M telemetry rows, multiple sources and expectations; benchmark 5,000-row ingestion followed by one evaluation cycle; record execution plans, buffers, wall time, queue lag, and lock duration at increasing source counts. Add indexes only when these measurements show a needed access path.
- Keep Phase-0 unit, data-integrity, day-2 integration, frontend/API (including 16 contract vectors), dashboard smoke, e2e, migration, and deploy-security suites green. Unit tests need no Core; database integration/performance require a disposable PostgreSQL; frontend/API and dashboard suites require an API/Core instance. Real deployment wiring is not part of E1.

## 8. Proposed work split

1. **E2 — additive schema and defaults** (≤10 files): migration after 008 for buildings schedule, expectation/gap/current tables and constraints; admin provisioning path; migration verification on disposable existing-volume copy. Depends on human decisions in §9.
2. **E3 — evaluator and job** (≤10 files): interval resolution, UTC/local schedule evaluation, incremental/idempotent gap and current-state writes, injected-clock unit and disposable-DB tests. Depends on E2.
3. **E4 — source correlation and read API** (≤10 files): source thresholds/grouping, authenticated freshness/gap endpoints, response tests and operator documentation. Depends on E3; does not change Core equipment state.
4. **E5 — consumers and rollout parity** (≤10 files): optional dashboard/chat/alert consumers, replace hardcoded alert time logic only after the zero-difference fixed-offset parity test, then selected-zone DST and performance checks. Depends on E2–E4 and explicit approval of the timezone/schedule.

## 10. Limitations to carry into the Phase 1 list

- No freshness evaluator, expectation configuration, persisted gap history, or current-freshness read model exists today.
- `data_sources` timestamps describe batch receipt/success/error, not per-asset reporting cadence; `connector_status` is opaque JSON diagnostics.
- Existing dashboard `no_data` and hourly heartbeat compliance remain separate legacy KPIs until a reviewed parity/consumer change.
- Fixed UTC+2 ignores DST and per-building differences; seed buildings and customer site timezone/schedule are not configured in the schema.
- Source-level grouping thresholds, holidays, active-window behavior, startup notification grace, and admin provisioning still require human decisions and site calibration.
- No ≥1M-row performance result is claimed; query plans and measured indexes are required before adding indexes.
