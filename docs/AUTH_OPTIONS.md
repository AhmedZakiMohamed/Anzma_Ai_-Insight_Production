# Authentication options: decision note

**Status: for human decision. No authentication model is selected by this note.**

## Current implementation

- **Source/connector ingestion:** `/api/v1/ingest/*` authenticates a per-source bearer key matching the `azk_<12-hex-prefix>_<secret>` shape. The service hashes the presented key with SHA-256 and compares it to the stored credential hash; successful credentials are associated with a source and checked for scopes. See [`app/services/ingestion.py`](../app/services/ingestion.py) and the credential contract in [`INGESTION_CONTRACT.md`, §11](INGESTION_CONTRACT.md#11-authentication-and-authorization).
- **Key lifecycle:** `scripts/ingestion_admin.py` provisions sources/keys and provides `rotate-key` and `revoke-key`. Rotation issues a second active key; the old key is revoked separately. The generated key is printed once. See [`scripts/ingestion_admin.py`](../scripts/ingestion_admin.py).
- **Operator REST and Socket.IO:** the replaceable `Authenticator` interface currently delegates to `EnvironmentBearerAuthenticator`, which checks the deployment's `ANZMA_API_TOKEN`. REST accepts a bearer token; browser session exchange sets an HttpOnly cookie; Socket.IO accepts the same deployment token or session cookie. See [`app/security.py`](../app/security.py) and [`app/main.py`](../app/main.py).
- The current operator credential is shared at deployment level; the current code does not identify individual users or assign user roles. This describes the repository implementation, not any customer environment.

## Source (connector) authentication options

| Option | Security properties | Rotation and revocation | On-prem OT/BMS operations and infrastructure | Failure modes | Fit with replaceable interface | Migration from today and likely code changes |
|---|---|---|---|---|---|---|
| **API keys (current)** | Bearer secret; TLS protects it in transit. Current implementation stores a SHA-256 hash and checks source binding and scopes. Possession of a key grants its assigned source permissions. | Current CLI can issue a second active key and revoke a key by prefix. Operators must distribute/store the new secret and retire the old one. | Lowest infrastructure burden of these choices: requires secure secret delivery and protected storage at the connector/site. The site must be able to reach the API over an approved network path. | Secret leakage permits use until revocation/expiry; lost secrets interrupt a connector; poor rotation coordination can cause downtime. | Already implemented behind the ingestion authentication service; other credential verification can be introduced behind a narrow credential-authenticator boundary. | No migration required. Hardening/rotation automation would change ingestion credential verification and CLI/secret-distribution procedures. |
| **Mutual TLS (mTLS)** | Client and server authenticate with certificates; private keys need protection. Can bind a certificate identity to a source. TLS client identity does not by itself define ingestion scopes. | Requires certificate issuance, renewal, trust-store updates, and revocation handling (for example, CA policy/CRL or short-lived certificates). | Requires a certificate authority or managed issuance, connector certificate installation, renewal monitoring, and proxy/API certificate validation. Site-specific OT change controls may add coordination; actual burden depends on site practices. | Expiry, clock errors, CA outage/rotation, trust-chain mismatch, or proxy misconfiguration can block ingestion. Revocation behavior depends on the chosen TLS termination and PKI setup. | Could be implemented at the TLS edge and mapped to the same source identity, or verified by an adapter implementing a credential interface. Proxy-to-application identity forwarding must be protected against spoofing. | Replace or supplement bearer-key verification; add certificate-to-source mapping and scope handling; configure TLS termination and credential lifecycle/operations. Existing keys may need a transition period. |
| **OAuth 2.0 client credentials** | Short-lived access tokens reduce the lifetime of a stolen token; authorization server can issue client identities/scopes. Security depends on issuer, audience, signing/key validation, and client-secret/private-key handling. | Rotate client secrets or signing credentials; disable clients/revoke grants at the authorization server. Access tokens may remain usable until expiry unless introspection or another revocation mechanism is used. | Needs an authorization server reachable from the site or connector, client registration, token endpoint availability, secure client credential storage, and token refresh support. | Authorization server/network outage, expired token, clock skew, issuer/key rollover, or unavailable introspection can interrupt ingestion. Offline/on-prem connectivity requirements need review. | A token validator can sit behind the replaceable authentication interface; source/scope claims must map to the existing source and permission model. | Add issuer/audience/scope validation and source-claim mapping, token refresh support on connectors, and authorization-server configuration/operations. Migrate key-based clients in stages. |

## Operator/user access options

| Option | Security properties | Rotation and revocation | On-prem operations and infrastructure | Failure modes | Fit with replaceable interface | Migration from today and likely code changes |
|---|---|---|---|---|---|---|
| **Shared deployment token (current)** | One high-entropy bearer credential shared by operators; current browser flow exchanges it for an HttpOnly, SameSite=Strict cookie. No individual identity or per-user role attribution. Use TLS in transit. | Rotate `ANZMA_API_TOKEN`; rotation invalidates existing sessions because authentication checks the configured token. Distribution is manual through deployment secrets. | Minimal identity infrastructure; requires secure distribution to each operator and protected deployment configuration. | Anyone with the token has the same operational access; loss/compromise requires broad rotation; operators cannot be individually distinguished. | Already supplied by `EnvironmentBearerAuthenticator` behind `Authenticator`. | No migration required. Fine-grained authorization would require user identity and authorization checks beyond replacing the token verifier. |
| **OIDC/SSO via reverse proxy** | Central identity provider authenticates users; a trusted proxy can enforce login and pass authenticated identity to the application. The application must trust only the proxy path and safely validate identity headers/tokens. | Disable users/sessions at the IdP; session lifetime and revocation depend on proxy/session configuration. | Requires an OIDC provider, proxy configuration, trust-boundary/network controls, and an operator identity lifecycle. Whether a site has an IdP or can reach it is unknown. | IdP/proxy outage, stale sessions, misconfigured header trust, or bypass access to the API can block access or undermine identity. | Can keep the application authenticator replaceable by adding a proxy-identity verifier; identity propagation and authorization mapping need an explicit interface. | Add trusted identity assertion validation and route authorization; configure proxy and session behavior; migrate operator login and any API clients. |
| **Per-user accounts with roles** | Individual accounts and role-based authorization can support attribution and least privilege. Requires secure password/session or federation design, account recovery, and authorization enforcement on each protected operation. | Per-user disable/reset and role changes; session invalidation and recovery policies must be defined. | Requires account administration, secure credential storage, recovery/support process, audit retention, and possibly MFA/federation infrastructure. | Account takeover, weak recovery, role misconfiguration, or account lockout can expose operations or prevent access. | Could implement a new authenticator and authorization layer, but current `Authenticator` answers only whether a token is valid; per-user roles need a richer identity/permission interface. | Largest application change: user model/store or federation, login/session management, role checks, audit attribution, UI/API client changes, and migration of shared-token users. |

## Recommendation (proposal, not decided)

Keep the current per-source key flow as the comparison baseline while requirements are gathered. For operator access, evaluate the existing shared-token flow against OIDC/SSO at the deployment edge if the site already operates a suitable identity provider; consider application-managed accounts only if required roles or audit controls cannot be met at that edge. This is a proposal for discussion, not an approved design or implementation plan.

## Decision: PENDING

The human decision owner should answer:

- Who installs, operates, and supports each site and its connectors?
- Does each site already operate an identity provider, certificate authority, or OAuth authorization server? Can the site reach it during normal operation?
- What audit attribution, retention, MFA, compliance, and revocation requirements apply?
- How many connectors and operator users are expected per site, and who distributes/rotates their credentials?
- Must ingestion or operator access continue during WAN, IdP, certificate-authority, or central-service outages?
- Are roles needed, and which operations should each role be allowed to perform?

Until these questions are answered, the authentication model remains undecided.
